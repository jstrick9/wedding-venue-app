## 1. Executive summary and verdict

The **Wedding Venue Intelligence Platform** is an unusually broad, locally-first wedding-venue operations and layout-planning product. Its domain model is its strongest asset and genuinely reflects how a real venue works (spaces, seating, chairs, linens, fixtures, lodging, decor, couples, packages, guest events, RSVP, wayfinding, rain contingency, weather, vendors, staffing, timelines, BEO, branding, backup, role-aware workflows, and a growing multi-tenant platform console).

**Current-state verdict (verified against HEAD, not historical notes):**

| Area | Assessment |
|---|---|
| **Local / single-browser mode** | Strong, healthy. Green gates. Suitable for demos, workshops, and controlled single-device use. |
| **Supabase backend / multi-user / multi-tenant** | **Still not production-ready.** The cloud seam is broader than at #173 (venue-specific login, platform console, tenant lifecycle, platform↔venue chat, branding, geocoding, cross-device couple snapshots) but remains a **partial synchronization layer**, not a fully-wired multi-tenant platform. Several P0/P1 items persist, and the **entire new platform-console layer (#176–#179) ships with zero automated test coverage and has not been smoke-tested against a live project.** |
| **Hosted single-file bundle** | Green, but has grown ~280 KB raw / ~72 KB gzip since #173 and still reaches external Google Fonts. |

**Most important architectural message (unchanged, now more urgent):** the product currently presents *some* workflows as shared/secure (platform console, venue login, tenant isolation, couple snapshots, platform chat) while the majority of the couple/guest/staff/calendar/package data that those surfaces claim to represent is still local-only. Either finish the backend as the authoritative source of truth per domain, or label each domain honestly as local-first. Do not present the hybrid as fully shared, secure, or real-time.

## 3. Status of the #173 P0/P1 baseline (re-verified against current code)

Several previously-flagged defects have been fixed since #173; several remain.

### Fixed / addressed since #173

- **P0-1 — Owner sign-up bootstrap.** `supabase/migrations/0001_initial.sql` now adds a `membership_bootstrap_owner` RLS policy permitting the first owner (whose `owner_id` matches the org) to insert the initial active owner membership; `AuthBackend.signUpWithSupabase` now *throws* on a failed membership insert rather than silently ignoring it. **Unverified live**, but the design is correct.
- **P0-4 — Supabase `owner` → local `basic`.** `AuthBackend.mapRole()` now maps `owner`/`admin` → `'admin'`. Restore and sign-in paths use it consistently. **Fixed in code.**
- **Split build (`build:split`).** The stale `yjs`/`y-websocket` manual chunks are gone; the command now builds successfully (with chunking-quality warnings, see §6).

### Still open (re-verified)

- **P0-2 — Cloud is not the complete data provider.** `SupabaseEntityRepository` still mirrors only a catalog-style subset (~28 domains). Couple events, couple guests, couple RSVP submissions, couple chat, packages/add-ons, guest events, venue map configs, venue rules, weather, calendar events, direct messages, staff/admin settings, and communication templates remain local. There is still no `CoupleEvent`/`CoupleGuest` → relational `events`/`guests` projection, so the venue portal's own couple/guest/RSVP views are not the server source of truth.
- **P0-3 — Legacy public guest RSVP RPC (`0002`).** `submit_guest_rsvp()` still (a) does not enforce `portal_access.enabled`, access start/end, event status, or RSVP deadline; (b) casts the JWT `sub` claim to `inet` for `submitted_ip` — a runtime error for authenticated callers and meaningless for `anon`; and (c) deletes-then-reinserts with no idempotency key or rate limit. The newer couple-portal path (`0005`) is better designed but still does **not** enforce an RSVP deadline or access window in SQL and does not validate the `p_submission` JSON schema.
- **P0-5 — Password reset.** `PasswordReset.tsx` is still a fully local flow and never calls the (otherwise unused) `requestSupabasePasswordReset()`. The "Continue as Planner Guest" entry point is now **hidden on platform and venue login screens** (`showPublicPortalLinks={false}` in `PlatformLoginScreen`/`VenueLoginScreen`), which is good progress, but the core cloud password-reset gap remains.
- **P1-1 — `org_data` broad member RLS.** `0003` still grants every active `is_org_member` read/write/delete on **every** domain in the same JSON table (including RBAC/security domains). UI hiding is still not authorization.
- **P1-2/P1-3 — Repository pulls bypass the event bus and domain event names don't match registry keys.** Not reconciled; silent split-brain risk on catalog/couple/map/chat sync persists.
- **P1-4/P1-5 — Layout cloud save is destructive replace-sync; empty remote results ignored.** `SupabaseLayoutRepository.saveAll()` still deletes/reinserts all rows with a fixed revision and no optimistic concurrency; `pullLayouts()` still skips writing when `remote.length === 0`.
- **P1-7 — Two RBAC authorities and role short-circuits.** The granular `PERMISSIONS`/`useRBAC` system and the legacy `UserPermissions` flags coexist; admin/staff early returns still bypass granular revocation.
- **P1-8 — Backup completeness and secrets in cleartext.** The registry still omits domains and the exported JSON still includes PBKDF2 password hashes/salts, portal password fields, and couple/guest invite tokens.
- **P1-9 — Server guest mode disconnected from couple guest management.** No transactional couple/guest projection into `public.guests`.
- **P1-11 — Invite acceptance does not refresh the active AuthContext.** `AcceptInvite` still just clears the hash via `onDone` after a timeout; it does not rehydrate the session/organization (a manual reload is required for new membership to take effect).

## 4. NEW findings: the platform-console layer (#176–#179) — reviewed as shipped code

This is the most security-sensitive new surface and it was reviewed here for the first time as-is. The migrations (`0006`–`0009`) and the new services/components are generally **well-architected** (clear separation of platform role vs. venue role, tenant-status-aware `is_org_member`/`has_org_role`, audited platform actions, security-definer RPCs that validate token length/hash/email/expiry, an `is_platform_admin()` gate on every console RPC, and a service-role-only geocode cache). The issues below are about completeness, test coverage, and a few boundary gaps — not a flawed core design.

- **N-1 — Zero automated test coverage for the entire platform console (#176–#179).** No test file references `PlatformAdminPortal`, `PlatformLoginScreen`, `VenueLoginScreen`, `VenueAdminOnboarding`, `PlatformVenueChatPanel`, `PlatformVenueMap`, `createVenueOrganization`, `get_platform_console_metrics`, `publicVenueService`, `platformBrandingService`, `platformChatService`, or `geocodingService`. This is the newest and most RLS/tenancy-sensitive code in the repo, and it ships with no unit/component coverage and no migration/RLS smoke test. Review #179 itself flags that "the final console changes require another complete test/coverage run before commit" and that live RLS/storage/chat/map tests remain pending — that work has not landed.

- **N-2 — Venue-admin onboarding invite token stays in the URL.** `buildVenueAdminInviteUrl` places the raw bearer token in `#/venue-onboarding?token=…`, and `VenueAdminOnboarding` never removes it via `history.replaceState`. This directly contradicts the AI-agent memory's own rule ("remove tokens from URLs with history.replaceState") and leaves the claim token in browser history / shareable URL after use. The token is SHA-256-hashed server-side and is a single-use admin invite, so exposure risk is limited, but it is inconsistent with the documented token hygiene.

- **N-3 — Couple snapshot payload stores raw bearer tokens in cleartext JSONB.** `couple_portal_snapshots.payload` intentionally contains guest `token` fields (the code that reads it does `guest_row - 'token'` to strip them on return), and the migration comment admits raw link tokens "remain inside the private snapshot." So guest/collaborator/couple bearer tokens are at rest (unhashed) inside the `payload` JSONB column. They are RLS-protected, but this is a secrets-at-rest smell and diverges from the "store only hashes" rule used for the dedicated token-hash columns.

- **N-4 — Platform console metrics are aspirational and will read zero in practice.** `get_platform_console_metrics()` aggregates `coupleEvents`, `coupleGuests`, and `coupleSubmissions` from `org_data`. But those domains are the **local-only** couple domains that the entity repository never mirrors (P0-2). Unless the couple→org_data projection is implemented, the console's `total_couples`/`total_guests`/`total_rsvps` and per-venue `couple_count`/`guest_count`/`rsvp_count` will be `0` for every real venue regardless of actual planning activity. The console should either implement the projection or label these metrics as "not yet populated."

- **N-5 — `geocode-venue` Edge Function has no rate-limit/throttle in front of public Nominatim.** It correctly verifies platform-admin Auth, uses a descriptive User-Agent/Referer, and caches. But there is no enforcement of Nominatim's 1-request-per-second rule; the only protection is the cache, and the review's own migration note acknowledges this. Bulk venue onboarding against the public service can still violate the policy and get the app's IP blocked. A self-hosted/managed Nominatim or a commercial provider is required before high-volume onboarding (as #179 states), but nothing in code throttles or hard-fails fast.

- **N-6 — Platform↔venue chat lets the client choose `sender_side`.** `sendPlatformVenueMessage(orgId, body, senderSide)` takes `senderSide` as a caller-supplied argument, and the RLS insert policy permits the two "platform→venue" and "venue→platform" combinations based on the caller's roles. A platform admin who is *also* a venue member can insert a message labeled `sender_side='venue'` (and vice-versa for a venue member who is also a platform admin). Minor trust-spoofing surface; the fix is to derive `sender_side` server-side from the caller's role rather than trusting the client.

- **N-7 — Multi-tenant metrics / chat / branding read patterns aren't covered by the metrics contract tests.** The `PlatformVenueMap` point/density/region/table views and the console directory operate directly on `listPlatformOrganizations()` (which does four parallel queries). No tests assert tenant isolation of these reads or that a non-platform-admin is denied.

- **N-8 — README and `.env.example` are stale vs. the platform console.** `README.md` still describes migrations `0001`–`0005` and the "cross-device" story as the backend path; it doesn't mention the multi-tenant platform console, venue-specific login, tenant lifecycle, platform chat/branding, geocoding, or migrations `0006`–`0009`. The memory's `9.8 Documentation precedence` correctly warns that older docs are stale, and this README is one of them.

## 5. Wedding-venue domain expert findings (fresh, beyond #173)

Grounded in how a real venue operates day-to-day. The product covers layout *planning* excellently; the biggest operational gaps are in **booking, revenue, day-of execution, and guest-to-operations projection.**

1. **Date-level availability is not operational availability.** The calendar model is `{date, startTime?, endTime?, spaceId?, category}`. There is **no space×time double-booking prevention**, no **setup/tear-down buffer** between events, no venue-wide **blackout windows** (e.g., "no weddings on Mondays", "Ceremony Lawn unavailable June–August"), and no **multi-space concurrency rules** (a 300-guest event that spans ceremony lawn + reception barn + parking must reserve all three atomically). `syncCoupleEventsToCalendar` auto-creates a single calendar row per couple event on `eventDate`, so two couples with the same date are simply shown side-by-side. For a real venue, this is the single most important planning gap.
2. **Guest RSVP does not project to venue-level catering/ops counts from one source of truth.** Meal/dietary tallies are computed inline in `CouplesPortal` and `CoupleManagement` (per couple), and `eventDashboard.ts` derives RSVP-response/capacity insights from a separate guest model. The executive `VenueDashboard` does not roll these up from a single projection, so "how many chicken/beef/veg and how many plus-ones for next Saturday across all events" has no authoritative answer. This is the classic "venue cannot do final headcount for catering until the week of" failure mode.
3. **BEO is a generated print document, not a controlled record.** It prints useful sections, but there are no **issued BEO versions**, no **change diffs**, no **locked-after-issue** behavior, and no **sign-off actor/timestamp** that would hold up as the venue's operational contract. The prior audit's "BEO sign-off is a print placeholder" still holds.
4. **Inventory is advisory, not a pull/return/reconciliation ledger.** Table/fixture counts exist, chair inventory is a warning (placement is not blocked), and linens/decor are not reconciled as a formal pull → setup → teardown → return inventory cycle. A real venue needs to know, per event, what was issued, what came back, and what is missing/needs ordering.
5. **No booking / contract / deposit / revenue lifecycle.** There is no lead/hold/booked/contracted/paid/completed/cancelled pipeline, no deposit tracking, no balance/contract management, and no revenue reporting. The console's venue metrics therefore cannot answer the business questions a venue owner actually asks (utilization, average ticket, deposit coverage, lost business). This is deliberate (the app is not an accounting tool) but it means "Intelligence Platform" KPIs are operational-only.
6. **Rotation-aware layout safety is still missing.** Collision/wall checks use axis-aligned boxes while the data model supports `rotation`; a rotated table/fixture can visually overlap or breach a wall without the validation model flagging it. High-risk for a day-of coordinator trusting the printout.
7. **Day-of coordination is manual.** The timeline is a schedule; there is no **vendor-arrival conflict detection**, no **timeline dependency warnings**, and no **incomplete-approval blocker** linking layout approvals → BEO issue → day-of go. These are cheap, high-value "intelligence" features the product is positioned to offer.
8. **Preferred vendor persona has no self-service account.** It is a curated directory with contact links — appropriate for a venue-managed preferred list, but the persona card in the memory suggests vendor self-service that does not exist.

## 6. Engineering / quality findings

1. **Bundle growth & chunking quality.** Single-file is now 2.07 MB / 481 KB gzip (+~72 KB gzip since #173) — driven by the platform console, map, geocoding, chat, and branding code. The split build warns on an **empty `vendor-react` chunk** (React is effectively landing in the 738 KB `chunk-admin`), and two modules that are meant to be lazy (`ObjectStorageService`, `guestPortal`) are statically imported elsewhere, so their dynamic imports do not split them. Code-splitting is therefore not delivering the intended first-paint benefit.
2. **Type-safety debt is concentrated and growing.** 24 runtime files use `@ts-nocheck` (unchanged count from #173), including the largest admin, dashboard, calendar, couple, vendor, and portal components. The green typecheck does not cover those files. ~170 `any` / ~89 `as any` in runtime code outside those files.
3. **11 tests remain skipped in high-risk areas.** Collision/assignment transitions, admin fixture/seating expansion, seating properties, and table↔room transitions. These are exactly the flows a day-of coordinator depends on.
4. **CI is lighter than the documented protocol.** No ESLint at all; `build:split`, coverage, unused-locals scan, and `npm audit` are documented as mandatory but are not in `.github/workflows/ci.yml`.
5. **Git history was flattened by uploads.** The current HEAD and most recent commits are `"Add files via upload"`; the meaningful `feat(platform):` history sits below squash-merge-style upload commits. Not a defect, but it makes bisecting regressions harder.
6. **External network dependency for fonts.** `config.ts` `loadGoogleFont` still injects Google Fonts, so even the "single-file" bundle makes network requests for typography. Document as "offline core, fonts external" or self-host.
7. **Good practice worth preserving (confirmatory).** PBKDF2 password storage + timing-safe compare; typed event bus with an enforcing linter; versioned storage envelopes with corruption recovery; Web Crypto opaque tokens for invites; CSV formula-injection protection; accessible `sr-only` file inputs with `<label>` bindings; shared SVG map renderer across admin/couple/guest/print/export; reduced-motion CSS; `max-h-[94vh]` modal overflow pattern; and the security-definer RPC discipline in the new migrations.

## 7. Prioritized remediation roadmap

### Phase 0 — Make cloud honest and safe (release-blocking)
1. Implement the couple/event/guest projection so the venue portal, couple portal, guest portal, and console metrics share one authoritative source of truth; **or** visibly label every local-only domain in cloud mode. Do not silently fall back to local after a cloud write error.
2. Enforce access window + deadline + field validation + idempotency/rate-limit in **both** guest RSVP RPCs (`0002` and `0005`); fix the `::inet` cast; return only safe fields.
3. Wire `PasswordReset` to Supabase Auth recovery in cloud mode and keep local reset demo-only.
4. Ship a real **migration/RLS smoke test** and a small **unit/component test suite for the platform console** (#176–#179) before claiming multi-tenant readiness.
5. Remove the onboarding invite token from the URL with `history.replaceState`; store no raw tokens in `payload` (hash-only); derive chat `sender_side` server-side.

### Phase 1 — Data integrity & security
1. Replace destructive layout replace-sync with row-level optimistic upserts + revisions.
2. Tighten `org_data` (role-aware domain allowlist or per-domain RLS/RPC); enforce least privilege.
3. Unify RBAC to one authority; remove role short-circuits; validate permission ids; cycle-detect inheritance.
4. Complete + redact the backup registry (secrets/credentials out of exported JSON).
5. Rehydrate active React state on repository pulls and make all persistence domain keys typed/consistent.
6. Add a client throttle / hard-fail for public-Nominatim geocoding and require a managed instance for bulk onboarding.

### Phase 2 — Quality & maintainability
1. Remove `@ts-nocheck` module-family by module-family (auth → admin → couple/portal).
2. Re-enable the 11 skipped tests; add browser E2E, axe accessibility, and multi-tab/device tests.
3. Add ESLint; expand CI to the documented gates (`build:split`, coverage, unused-locals, `npm audit`).
4. Fix the split-build chunking (remove/repair `vendor-react`, verify lazy boundaries actually split) and self-host fonts.
5. Update README/`.env.example`/docs to reflect the multi-tenant console.

### Phase 3 — Wedding intelligence that differentiates
1. Space×time double-booking + setup/tear-down buffers + blackout windows + multi-space atomic reservation.
2. Authoritative per-event catering/headcount roll-up from a single RSVP projection.
3. Issued BEO versions + change diffs + sign-off actors/timestamps + lock-after-issue.
4. Pull/return inventory reconciliation for chairs/linens/decor.
5. Rotation-aware collision validation.
6. Day-of decision support: vendor-arrival conflicts, timeline dependencies, incomplete-approval blockers.
7. (Optional product scope) lead→booked→contracted→paid pipeline and deposit/revenue metrics.
